### 1.6 UDP → 解析 → Socket 推送 → 前端消费（全链路实测）

| 指标 | 数值 | 方法 |
|---|---|---|
| 单包解析耗时 | **3.59 µs**（27.8 万包/秒） | `parseTelemetryPacket` 20 万次循环 |
| 60Hz 下解析 CPU 占用 | **215.6 µs/秒**（0.02%） | 同上换算 |
| 端到端时延（UDP 发出 → 浏览器收到 `telemetry` 事件） | p50 **1.4ms**，p90 **2.2ms**，p99 **23.0ms**，max 23.0ms | 200 包，逐包携带发送时刻 |
| 60Hz 输入下的投递率 | **45.2%**（600 包 → 271 次事件） | 10 秒洪泛，服务端 33ms 节流 |
| 单帧推送载荷 | **1,699 B** → 30Hz 下 50 KB/s | `/api/current` 响应体 |
| 服务端 RSS | 空载 74.0MB；带合成数据 98.4MB；保存后 92.4MB | `ps -o rss` |
| 高频洪泛（≈1000 包/秒）期间 `/api/status` | median **1.7ms**，max 8.2ms | 事件循环未被阻塞 |

结论：**UDP 接收与解析不是瓶颈**；33ms 节流是主动防风控设计（60Hz 输入只推 30Hz），时延预算全部落在这一层（p50 1.4ms，说明节流门一旦放行即立即送达）。

#### 2.1.2 瓶颈点（按实测收益排序）

1. **`processTelemetryPacket` 里的「每包车辆记账」**（`index.js:168-199`）。`vehicles[ord].lastUsed = new Date().toISOString()` 每包都执行（30–60 次/秒的 ISO 字符串分配）。可改为「值变化才更新 + 5s 限频落盘」，行为等价（`lastUsed` 只被用于 `/api/sessions` 的就近匹配）。
2. **`recordStats` 广播风暴**（`record.js:414-421`）：
   ```js
   const packetCount = stateManager.getPacketCount();   // 恒为 0！
   if (packetCount % 30 === 0) { stateManager.io.emit('recordStats', {...}) }
   ```
   全仓库 `setPacketCount` **0 次调用**（`state-manager.js:50-51` 定义了 getter/setter，只有 getter 被用）→ `0 % 30 === 0` 恒真 → **录制期间每个包都广播一次 `recordStats`**（约 20–30 次/秒），前端 `Header.jsx:103-107` 每次都 `setRecordDuration` → Header 跟着 30Hz 重渲染。
3. **`handleAutoRecord` 里的空 if 块**（`record.js:405-412` 与 `record.js:439-443`）：`if (track.turns && track.turns.length > 0) { }` 与 `if (track.turns && track.turns.length > 0 && isPositionValid) { }` 两个空块，每包都做 `stateManager.getTrackMode()` + 属性检查。属死逻辑残留（可删，等价）。
4. **前端 30Hz 全树重渲染**（见 2.2）。

### 2.2 前端主线：渲染路径、构建产物、内存与事件循环

#### 2.2.1 渲染路径（高频重渲染）

```
io.emit('telemetry') 30Hz
  → useSocket.js:88  telemetryListeners.forEach(...)     ← 全局单例 Set
  → DashboardPage.jsx:14  setTelemetryData(telemetry)     ← 每帧新对象，必触发渲染

       ├ PaceNotesPanel    (position 每帧新对象 → useEffect 每帧重跑，见 2.2.2)
       ├ BrakingGripDynamicsPanel (两个 useEffect 每帧 setState(peakG*))
       └ RacePerformanceTimingPanel
```

证据与评估：

| 问题 | 位置 | 影响 | 备注 |
|---|---|---|---|
| 仪表盘无渲染隔离 | `DashboardPage.jsx:13-14` + 各面板直接吃 `data` prop | 30Hz 下整棵树（含约 200 个内联 style 对象重建）重渲染 | 未做浏览器 profiling → **帧率影响未验证** |

4. **门禁收益**：`lint:dead`（knip）当前绿灯依赖 D3/D4 的删除；还原它们会立刻让 `npm run lint:dead` 失败。

### 7.3 结论性建议（默认口径）

> **默认维持删除，需要时按 git 历史还原。**
>
> 理由：这些内容都是①永不执行（字面量 `false` 短路）或②绑定级 0 引用（含级联死链）或③无 import 的文件；保留它们不产生任何功能，只增加阅读成本、误导后续 Agent，并让 `lint:dead` 失效。它们的「原样」保存在 git 历史中，还原成本是单条 `git checkout`，因此删除的可逆性足够高。
>
> **唯一例外（必须修正，不是「还原」）**：D10 的 `lastLapNumber`。它的删除方式错了——删了声明却留下写入，导致 P0 回归。正确处置是**删掉那行写入**（批次 0），而不是恢复声明。
>
> 若主人确实打算**重新启用**「改装详情展开区域」或「多圈分段计时对比表」，请告知，那时的正确路径不是 `git checkout` 旧代码，而是按当前设计重做（旧实现的 props 契约已经和现在的 `useTuneManager` 不匹配）。
